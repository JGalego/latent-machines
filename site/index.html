A notebook for a language model

Who's bringing dessert?

You're at the grocery store with a cake in your cart. Before you check out, you ask an assistant whether anyone's bringing dessert to the potluck. In the group chat, Maya offered to bring dessert, then wrote, “I'll bring bread instead.” The assistant misses the update. “Maya's bringing dessert,” it says. You put the cake back.

In a notebook, you'd give Maya one line. Cross out dessert, write bread, and you can check what she's bringing without rereading the chat. We tried giving a model a notebook of its own. It could ask in words or fill in the blanks: which entry, what to do, and what to write. The fill-in-the-blanks version is what we mean by a typed interface.

We tested this on fixed instructions, not group chats. The notebook, built with either ordinary code or neural-network arithmetic, kept the same record when given the same commands. The model got worse at choosing those commands as the list grew. On this small task, it stopped making mistakes when we gave it one instruction at a time.

How the model used the notebook

The same notebook, two ways to ask

We gave a model a list of updates and asked it what was in the notebook along the way. We used numbers instead of potluck dishes so we could check every answer.

{{example:record-updates}}

One version of the model read the notebook's replies as text. In the other, the number went straight to the part of the model that answers questions. The direct reply helped on longer lists and with combinations of entries and numbers the model hadn't seen. On short lists, the difference was too small to draw a clear conclusion ({{tab:e02-566e}}).

{{example:reply-formats}}

The text version actually picked the right commands more often. Its disadvantage showed up when it used the replies. Replacing the notebook's ordinary code with neural arithmetic changed no answers. And as the lists grew, every version got worse.

{{anim:e02}}

In {{e:E02}}, we left the language model unchanged and trained only small add-ons, called heads, to choose commands and answer questions. We trained on short lists and tested on longer ones too. A wrong command could change the notebook and spoil a later answer.

Look it up, then copy it

Now ask the model to copy a number from one notebook entry to another. The instruction doesn't say what the number is. The model has to look it up before it can write it down.

{{example:copy-an-entry}}

In {{e:E03}}, we sent each command and reply back through the model as a list of numbers, called a vector, instead of as text. Then we tried giving the model the same trained vector every time. That vector told it nothing about the notebook's reply; the reply went directly to the heads that chose what to do next.

{{anim:e03}}

The version that got the same vector every time did at least as well as the version that got the reply, except on the longest lists we tested. Both did better than the other approaches.

{{feedback_grid}}

Most of the gain came from giving the model an extra trained input, even when that input didn't tell it what happened. That extra input also gave the model more to process. The notebook itself matched the reference at every step ({{tab:e03-ff00}}).

One instruction at a time

The notebook wasn't losing numbers, but the model still made more mistakes on longer lists. In {{e:E09}}, we went back to the first test, without the copy instructions. This time the model saw just the current instruction and a short reminder of the task. The notebook kept the numbers from earlier lines.

{{example:one-line-at-a-time}} {{anim:e09}}

Reading one line at a time, the model made no mistakes on the lists we tested. The versions that kept earlier instructions in view struggled as the lists grew. The one-line version saw less at once, but read more in total than the version that used the same interface and kept the earlier lines in view.

{{length_charts}}

We wrote down our predictions before the run. Reading one line at a time beat reading the running list, as predicted. But we couldn't test how mistakes add up when there were none. We also underestimated what the model could do without a notebook: guessing the starting value worked whenever an entry hadn't changed.

There was a catch: the model had seen every update used in the first test. We left some out of training and tried again. The model handled most of the new updates, better than a model with no pretraining but still short of our target. Reading one line at a time also helped on lists that included those updates. Each line still made sense on its own.

How we checked the notebook

Check every step, not just the answer

Was the command wrong, or did the notebook get it wrong? We send each command to two notebooks: one built with neural-network arithmetic and one written separately in ordinary integer code. After each command, we check what both notebooks said and what they kept.

{{example:wrong-command}}

A correct reply can hide a small error. If a stored 1 slips to 0.999, it still reads as 1. We measure that drift, which we call residue. We also check that a saved copy of the notebook restores it exactly.

The exactness checks in equations

The machine's rules specify the next state \(s'\), an event \(e\) (continue, output, halt, or fault), and a work count \(w\) for each state \(s\) and action \(a\):

$$ T : (s, a) \mapsto (s', e, w), \tag{{{eqtag:transition}}} $$

Invalid actions return a fault and leave the state unchanged. At each step we compare events, work counts, and the decoded state, \(\mathrm{dec}(\sigma_t) = s_t\). We stop at the first mismatch. The controller sees the reply, never the full state used to check it ({{fig:components}}).

Residue is the largest distance of any stored bit from the nearer of 0 and 1:

$$ \rho(\sigma) = \max_i \, \min\!\big(|\sigma_i|,\ |\sigma_i - 1|\big), \tag{{{eqtag:residue}}} $$

Halfway through each run, we save the decoded state as JSON and rebuild the tensor from it. For these bit-based machines, exact means every step matches, no bit drifts, and the rebuilt tensor equals the live one.

One column per slot

Think of the notebook as a row of drawers. To replace a number, open just its drawer, take out the old number, and put the new one in. In the neural version, each drawer is a column in a grid of bits. A key with one 1 and the rest 0s selects a single column. That's one-hot addressing.

The arithmetic clears that column by subtracting it from itself, then puts the new bits in its place. The other columns stay untouched. That only works exactly if the arithmetic keeps those 0s and 1s intact. The demo shows how a tiny change can make a number fade away.

The memory update in equations

We use the state update from Gated DeltaNet {{cite:gdn}}. The key \(k_t\) selects where to write \(v_t\), and the query \(q_t\) selects what to read. The gate \(\alpha_t\) controls how much old state survives, and \(\beta_t\) controls the write:

$$ S_t = \alpha_t\, S_{t-1}\big(I - \beta_t k_t k_t^\top\big) + \beta_t\, v_t k_t^\top, \qquad o_t = S_t q_t. \tag{{{eqtag:delta}}} $$

For \(N\) slots of \(B\) bits each, \(S\) has shape \(B \times N\). We keep \(\alpha_t = 1\), set \(\beta_t = 1\) to write and \(\beta_t = 0\) to read, and use \(x / \max(\lVert x \rVert, \epsilon)\) to leave one-hot selectors unchanged. We evaluate the update without building the full \(N \times N\) matrix. No sum combines two nonzero terms, so an update starting from bits stays exact in binary floating point.

A switchboard for rules

A finite-state transducer remembers which of a fixed set of states it's in. One that tracks whether a count is even or odd has just two. Think of its rule table as a switchboard: the current state and the new input light up one row, which tells the machine what to output and which state to enter next.

In the two-layer circuit, the state \(s\) and input \(x\) are both one-hot. ReLU clips a negative number to zero; the active pair adds to 2 before subtracting 1, so only its row survives:

$$ z = \mathrm{ReLU}\big(W_{\mathrm{in}} [s; x] - \mathbf{1}\big), \qquad s' = W_{\mathrm{next}}\, z, \qquad y = W_{\mathrm{out}}\, z. \tag{{{eqtag:lookup}}} $$

There is one hidden unit for every state and input pair, with four nonzero weights per unit. The largest intermediate value is 2. We test even/odd parity, a counter that wraps at five, and a machine that tracks the order of three items as neighbors swap places.

A stack of plates

A stack works like a pile of plates: add to the top, take from the top. That is useful for matching brackets because the last bracket opened is the first one that must close. We store up to \(N\) items in the same memory matrix. A one-hot pointer \(p \in \{0,1\}^{N+1}\) records the depth; the shift matrix \(U\), with \(U_{d+1,d} = 1\), moves the pointer up a slot:

$$ \begin{aligned} \textsf{push}(v)&:\quad S \leftarrow S + (v - S p_{1:N})\, p_{1:N}^\top,\quad p \leftarrow U p, \\ \textsf{pop}&:\quad p \leftarrow U^\top p,\quad o = S p_{1:N},\quad S \leftarrow S - (S p_{1:N})\, p_{1:N}^\top. \end{aligned} \tag{{{eqtag:stack}}} $$

Taking an item clears its slot. The pointer's end positions mark a full or empty stack, where pushing or popping, respectively, returns a fault.

When a number won't fit

Bits are easy to store exactly. Larger integers and small changes can be harder. With bfloat16, every whole number through 256 is representable; above 256, some are skipped. 257 can round to 256 and look like a perfectly good integer. That's why we check the result against an independent reference as well as measuring residue.

{{e:E04}}. Picture a worksheet: some calculations can start right away, while others need earlier answers. Doing the ready calculations together took fewer rounds, but ordinary Python was still faster on single inputs. It helped to process inputs in batches, though the tensor versions didn't consistently beat the integer tensor baseline. The higher-precision versions matched the reference; some lower-precision results rounded to the wrong integer without showing any drift.

{{anim:e04}}

{{e:E05}}. To find which places are connected, start with direct links and add routes built from the links you already know. Most versions matched the reference, but bfloat16 rounded some longer distances. On maps with relatively few links, conventional graph algorithms were faster.

{{example:linked-roads}} {{anim:e05}}

{{e:E06}}. Grid rules like the Game of Life matched cell for cell. Filters that reshape a signal stayed within the allowed error at higher precision, but most bfloat16 versions didn't. A small rounding error can make a filter forget a signal much sooner than it should.

{{anim:e06}}

{{e:E07}}. An optimizer usually nudges numbers toward a target. In this test, a single gradient step with one-hot addressing and a learning rate of 1 replaces the old value exactly in float32 and float64. Smaller steps leave some of the old value behind. Momentum carries history across steps, so a snapshot of the slots alone can't restart it. In bfloat16, momentum exceeds the error tolerance, and the decay factor rounds to 1, so stored values never fade.

{{anim:e07}}

{{e:E08}}. Within the stated bounds, the tensor checker agreed with the reference and was faster than the Python checker. Outside those bounds, a low-precision version rejected some valid answers. A faster checker didn't make our search better than WalkSAT, and only the complete solver proved that some puzzles had no solution.

What we haven't tested

The exactness checks cover small machines on finite workloads. They don't tell us how the machines behave at larger sizes, in a full Gated DeltaNet layer, or in its fused or chunked GPU kernels. Ordinary code checks addresses and values before the tensor update. The checks cover what happens once the machine receives a command, not whether a neural layer could validate it. Timings from shared CPUs are rough comparisons.

The controller experiments use one model and one family of tasks. We added E03's control after a pilot and didn't test input vectors that carry the reply without the action. E09 reused the same small set of unseen instructions across runs, so the repeated scores don't tell us how many other instructions the model could handle.

The next instruction

Back in the potluck chat, “I'll bring bread” makes sense on its own. “I'll bring that instead” only makes sense if you know what someone just suggested. That's our next test: can the model still read a short stretch at a time when one line depends on another?

For now, a small controller talks to memory that sits outside the model. We plan to put memory inside a model layer, then test whether the controller can learn from feedback on its answers without being shown the right commands. The notebook works on the tests so far; we don't yet know whether building it into the model will help.

Where the idea comes from

Other projects have turned programs into neural-network weights {{cite:tracr,alta,looped}}. Qwenputer puts a RISC-V CPU in a language model's layers; QwenFX uses it to run a coding agent {{cite:qwenputer,qwenfx}}. Percepta and chipformer use attention over an execution log for WebAssembly and CHIP-8 {{cite:percepta,chipformer}}. Neural Comprehension and Tracr-Injection explore other ways to connect compiled programs to a language model {{cite:comprehension,injection}}.

Earlier learned controllers use explicit memory or learn to drive program instructions {{cite:ntm,dnc,npi,nram,nhc,forth}}. ToolkenGPT teaches a frozen model which tool to call, with arguments passed as text {{cite:toolken}}. We compare typed and textual interfaces on the same task, then swap the machine beneath the typed interface to see what changes.

The memory update here comes from work on fast weights and linear attention {{cite:fwp}}. Other linear recurrences extend what state a network can track, including tasks such as parity and permutations {{cite:negeig,deltaproduct}}.
